# ragbot 工作计划

## 工作规则

- 每项新工作先在本文件写目标、范围、验收条件和测试计划，再从非 `main` 的工作基线创建任务分支。
- 在任务分支完成实现与验证；实际改动记入 `issues.md`，测试结果记入 `test.md`，发现和修复的缺陷记入 `bug.md`。
- 任务完成、测试通过且记录齐全后，才能合回原非 `main` 分支。合入 `main` 必须由用户明确提出；未经该指令不得合入 `main`。
- 失败的测试必须先修复或明确记录为未完成；不能把未通过的任务标为完成。

## 后续研发计划：提高离线问答的通用性

依据 `可追溯知识库问答研发任务书-叶绍康.md`，按独立任务分支逐项推进；每项开工前补充该项的验收条件和测试案例。

以上为计划，完成情况以对应任务分支的代码、测试与记录为准。

## 已完成：V1 跨版本指针证据链（references/inherits）

**讨论结论：**当前版本采用“最小必要闭包”，不搭建通用图遍历框架。关系字段保留扩展点，但 V1 只实现 `references` 与 `inherits`；不实现 `contradicts` 自动处理、多跳遍历、模型推理或图数据库适配。现有文档级 `Document.Replaces` 继续走原有版本裁决路径，作为混合架构的逃生舱。

**目标：**识别明确的“沿用/引用”指针句，建立可审计的 Section 级关系；查询命中指针块时最多跟随一跳，明确展示现行文档的指针声明和被引用版本的具体条款，禁止把旧条款伪装成新版本原文。

**范围：**扩展 Chunk/关系数据结构保存关系类型、源指针原文和目标文档/版本/Section；导入阶段只做显式目标的语法解析，`parsed` 不代表目标存在，缺失目标在查询时拒答；回答阶段实现具体的单跳 `inherits` 解析与 `references` 来源定位，目标不唯一、缺失、循环或版本/范围不匹配时拒答。保留现有 `Replaces` 逻辑，不写通用 `TraverseGraph`。

**原工作分支：**`work/ragbot`。

**任务分支：**`feature/document-pointer-relations`；完成后仅合回 `work/ragbot`，不合入 `main`。

**当前状态：**实现、聚焦测试、全量 Go 测试、隔离演示评测和代码审查已通过；任务分支无冲突合回 `work/ragbot`，`main` 未合并。`feature/delivery-validation` 的独立保留集失败属于另一未合并任务，本项不改写其结果。

**验收条件：**

1. v2 的明确指针句能解析到 v1 的指定 Section，并保存源 Chunk、目标文档/版本/Section、关系类型和原始指针文本。
2. `inherits` 最多跟随一跳；回答同时引用 v2 指针句和 v1 具体条款，明确标注“具体条款来自 v1”。

5. `references` 与 `inherits` 的行为有明确测试；不实现 `contradicts`、任意深度遍历或模型关系发现。
6. 维护 `issues.md`、`test.md`、`bug.md`，记录实际改动、测试结果、未解决限制和合并状态。

**测试计划：**用虚构 v1/v2 文档写聚焦测试，覆盖明确单跳继承、明确引用、目标缺失、目标 Section 歧义、循环/多跳拒答、当前版本与历史版本、范围不匹配及旧版本回归；实现后运行聚焦测试、`go test -count=1 ./...`、`go vet ./...`、格式/空白检查，并核对 `Replaces` 原有测试。
